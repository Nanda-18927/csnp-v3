# Database

SQLite, one file: `backend/crimesight.db`. Six tables, seven indexes, no ORM.
Schema lives in `database/schema.sql` and is executed at startup.

---

## 1. Tables at a glance

| Table | Rows | Holds |
| --- | ---: | --- |
| `police_stations` | 6,006 | every station in South India, with coordinates |
| `criminals` | 211 | tracked persons and their profile |
| `officers` | 190 | the serving roster |
| `cases` | 275 | FIRs, each linked to station, officer and criminal |
| `criminal_links` | 854 | the relationship graph between criminals |
| `users` | 3 | accounts, with role and clearance |
| `password_resets` | 0 | in-flight reset tokens (hashed) |
| `citizen_requests` | 0 | requests raised by public users, routed to a station |
| `citizen_request_messages` | 0 | the negotiation thread on each request |

`password_resets` is empty between resets by design — rows are deleted once
expired or spent. The two `citizen_*` tables start empty as well and fill up
as citizens send requests.

---

## 2. Entity relationship

```
police_stations ──┬──< cases >──┬── officers
   id (PK)         │             │
                   │             └── criminals
                   │                   id (PK)
                   │
                   └── criminal_links (graph, not a FK relationship)
                             a ── criminals.id
                             b ── criminals.id

users   ── standalone; linked to nothing. Credentials only.
password_resets ── username ──▶ users.username
```

`criminal_links` is deliberately not a foreign key. A link is an *inferred*
relationship ("these two share a handling officer"), not a declared one, and
the graph would be far more rigid with real constraints on both ends.

## 3. Table reference

### `police_stations`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | INTEGER PK AUTOINCREMENT | internal key used by `cases` |
| `ps_code` | TEXT NOT NULL UNIQUE | the official police station code |
| `name` | TEXT NOT NULL | e.g. `Thiruvananthapuram Railway` |
| `district` | TEXT NOT NULL | |
| `state` | TEXT NOT NULL | 8 states/UTs |
| `lat`, `lng` | REAL NOT NULL | drives the 3D map projection |
| `sector` | TEXT | |

Indexed on `state` (`idx_stations_state`) — the map's state filter.

### `officers`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | TEXT PK | `OFF-SI-001` |
| `name` | TEXT NOT NULL | |
| `squad`, `rank` | TEXT | `rank` drives the roster-wall column height |

190 rows. Note the *distinction* from `users`: an officer is a serving record in
the case system; a user is a login. They are unrelated tables and an officer
need not have an account.

### `criminals`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | TEXT PK | `CRIM-SI-1002` |
| `name` | TEXT NOT NULL | |
| `age` | INTEGER | |
| `address`, `city`, `state` | TEXT | |
| `gender`, `alias` | TEXT | |
| `photo_id`, `photo_url` | TEXT | portrait for the dossier |
| `crime_type`, `status`, `station`, `officer`, `case_ref` | TEXT | dataset provenance |
| `lat`, `lng` | REAL | where the record is plotted on the map |

One record in the seed set (`CRIM-111`, "Debug Subject") is a deliberate
fixture for exercising the create-criminal path.

### `cases`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | INTEGER PK AUTOINCREMENT | |
| `fir_number` | TEXT NOT NULL UNIQUE | `FIR-2026-4605` |
| `station_id` | INTEGER | → `police_stations.id` |
| `officer_id` | TEXT | → `officers.id` |
| `criminal_id` | TEXT | → `criminals.id` |
| `severity` | TEXT NOT NULL | Critical / High / Medium, **derived from crime type** on create |
| `crime_type` | TEXT NOT NULL | |
| `crime_count` | INTEGER | charges |
| `status` | TEXT NOT NULL | Open / Under Investigation / Closed |
| `completion_pct` | INTEGER | drives the progress bar |
| `handling`, `investigation_type` | TEXT | |
| `arrest_date`, `remarks` | TEXT | |
| `transfers`, `experience_years` | INTEGER | |

`severity` is computed server-side by `get_severity(crime_type)` rather than
trusted from the client, so a caller cannot register a homicide as medium.
Editing the crime type re-derives it unless a severity was pinned explicitly.

Indexed on `station_id` and `criminal_id` — the two columns every
"cases for X" query joins on.

> **Known data quirk:** `handling` is the literal string `"Direct"` in every
> seeded row. It carries no information and is displayed verbatim in the case
> dossier. It is a source-data property, not a rendering bug.

### `criminal_links`

| Column | Type | Notes |
| --- | --- | --- |
| `a`, `b` | TEXT | the two criminal ids |
| `kind` | TEXT | `officer`, `station`, `city`, `crime` |
| `strength` | INTEGER | 1–3 |
| `label` | TEXT | human reason, e.g. `Shared officer: Inspector …` |
| PK | (a, b, kind) | |

Generated by `imports/import_datasets.py`. Indexed on `a` and `b` separately —
a single composite index cannot serve "all links where b is X".

### `users`

| Column | Type | Notes |
| --- | --- | --- |
| `username` | TEXT PK | |
| `password` | TEXT | scrypt hash via werkzeug — never returned |
| `role` | TEXT | `public` / `police` / `admin` |
| `display` | TEXT | shown in the UI |
| `email`, `phone` | TEXT | at least one required at signup; the reset route |
| `badge`, `rank`, `squad`, `official_id` | TEXT | police / admin profile |
| `station_code`, `station_name`, `district`, `state` | TEXT | posting |
| `designation`, `department`, `zone` | TEXT | admin profile |

Partial **unique** indexes on `email` and `phone`
(`WHERE … IS NOT NULL AND … != ''`), so two Public accounts cannot share a

## 4. Seed data

### `database/seed.sql` — the demo fixture

25 stations · 20 officers · 11 criminals · 75 FIRs · 3 users · 3 users' links.

Applied **only when `police_stations` is empty**. Creates the three demo
accounts: `admin` / `govt2026`, `officer` / `police123`, `public` / `public123`.

### `database/south_india.sql` — the real dataset

Generated, ~7,400 lines: 5,981 stations, 200 criminals, 854 relation edges.

Applied **only while the station table still holds the 25-row demo seed** —
a floor of 1,000 rows in `database.py` decides this. That guard is why
restarting the server never re-imports over your data.

### `data/` — the source workbooks

| File | Size | Rows |
| --- | ---: | ---: |
| `India_Police_Stations_Full_Database.xlsx` | 674 KB | 5,981 |
| `South_India_Criminal_Tracking_200.xlsx` | 24 KB | 200 |

### `imports/import_datasets.py`

Compiles the workbooks into `database/south_india.sql`. Standard library only —
an `.xlsx` file is a ZIP of XML, so no pandas or openpyxl is needed. A workbook
of 5,981 rows unzips and parses in a couple of seconds.

```powershell
python imports/import_datasets.py          # rewrite the SQL
python imports/import_datasets.py --apply  # …and load it
```

Re-run after editing either spreadsheet.

## 5. Constraints in force

| Constraint | Why |
| --- | --- |
| `ps_code` UNIQUE | it is the real-world identifier |
| `fir_number` UNIQUE | an FIR number is issued once |
| `criminal_links` PK (a,b,kind) | no duplicate edges of the same kind |
| partial UNIQUE on `users.email` / `users.phone` | two accounts must not share a reset route |
| `NOT NULL` on identity columns | a station without coordinates cannot be plotted |
| `PRAGMA foreign_keys = ON` | `cases` → station/officer/criminal integrity |
| CHECK-free status/severity | values are constrained in the application layer, not the schema — a deliberate trade for portability |

That last row is a real trade-off. SQLite would accept the CHECK constraints,
but they were left to the application so the same `.sql` files remain loadable
by tools with stricter or looser dialects.

## 6. Migrations

No Alembic, no migration files. `backend/database.py` holds an allow-list of
columns that newer versions add:

```python
_USER_COLUMNS = (
    ("badge","TEXT"), ("rank","TEXT"), …, ("email","TEXT"), ("phone","TEXT"),
)
```

On every start, any missing column is added with `ALTER TABLE … ADD COLUMN`.
Idempotent, and enough for this project's rate of change.

Adding a column to `schema.sql` **and** to `_USER_COLUMNS` is the whole process.
Renaming or dropping a column needs hand-written SQL — there is no down-migration
machinery, by design.

---

## 7. Backup and reset

```powershell
Copy-Item backend\crimesight.db backend\crimesight.db.bak
```

To start clean, delete the database and restart — the schema and both seed
files re-run automatically.

## 8. Query performance

Indexes exist for exactly the joins the app performs:

| Index | Serves |
| --- | --- |
| `idx_stations_state` | the map's state filter |
| `idx_cases_station` | "cases filed at this station" |
| `idx_cases_criminal` | the criminal dossier's FIR history |
| `idx_links_a`, `idx_links_b` | the wheel graph, both directions |
| `idx_users_email`, `idx_users_phone` | reset lookup |

Every page's aggregate queries are single-pass `COUNT`/`SUM` over `cases`, which
at 275 rows is sub-millisecond. The scale at which this stops being true is far
beyond this dataset.
